## Overview

The **Smart Home / IoT Device Monitoring System** provides residential property owners and facility managers with real-time telemetry, automated climate and lighting control, security surveillance oversight, and database management for connected IoT hardware.

The platform combines a relational **Oracle Database 21c** schema (17 normalized tables with stored procedures, explicit cursors, and triggers) with server-side access control (`HOME_ACCESS`), a dual-method **Firebase Authentication** layer (Google OAuth and Email/Password), an in-app **SQL & PL/SQL Query Console**, and an interactive architectural **3D Digital Twin** rendered with Three.js.

---

## Features

- **Multi-Method Firebase Authentication:** Seamless Google OAuth and Email/Password authentication with automated user provisioning and Firebase UID linking into Oracle.
- **Role-Based Authorization:** Server-enforced `ADMIN` vs. `USER` privileges. Regular users are strictly isolated to homes granted via the `HOME_ACCESS` associative entity.
- **Multi-Home Selector & Dashboard:** Switch between accessible residential estates, create new homes with atomic owner provisioning, or inspect global analytics.
- **Subtype-Specific Device Management:** Tailored controls and telemetry cards for **Smart Lights**, **Thermostats**, **Temperature Sensors**, **Motion Sensors**, and **Cameras**.
- **Real-Time Device Control:** Instant status toggles (`ONLINE`, `OFFLINE`) and configuration updates backed by Oracle transactions.
- **Diagnostic Health Reports:** Streamed diagnostic reports generated by Oracle PL/SQL stored procedures using explicit cursors and `DBMS_OUTPUT`.
- **SQL Query & PL/SQL Console:**
  - 5 Categorized Template Dashboards: `[ SELECT ]`, `[ INSERT ]`, `[ UPDATE ]`, `[ DELETE ]`, and `[ PL/SQL ]`.
  - Scoped `USER` DML: Regular users can execute real database mutations strictly within their accessible homes.
  - Sensitive Identity Protection: Unconditional lockdown on `USERS`, `USER_CONTACT_NUMBERS`, and `HOME_ACCESS`.
  - Approved Stored Routines: Invocations for `FN_CALCULATE_DEVICE_UPTIME`, `FN_CHECK_DEVICE_ACCESS`, `SP_ACKNOWLEDGE_ALERT`, `SP_HOME_DEVICE_HEALTH_REPORT`, and `SP_RECORD_SENSOR_READING`.
  - Database Trigger Testing: Automated cycle prevention validation testing `TRG_PREVENT_DEVICE_CYCLE`.
- **3D Digital Twin (`visual.html`):** Interactive Three.js spatial digital twin rendering physical devices, room layouts, status lighting, and temporary in-memory console commands.
- **Comprehensive API Verification:** Postman/Newman end-to-end test collection with automated assertions across all controllers.

## Architecture

The system follows a 3-tier architecture with backend-authoritative security:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           Client Presentation Layer                     │
│  React 19 SPA (Vite)  ·  Tailwind CSS 4  ·  Three.js Digital Twin       │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ HTTPS / Bearer Token
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                            API & Business Layer                         │
│                    Spring Boot 4.x / Java 21 REST API                   │
│                                                                         │
│  ┌───────────────────────┐  ┌────────────────────────────────────────┐  │
│  │ Firebase Admin SDK    │  │ Spring Security / JWT Filter           │  │
│  │ Token Verification    │  │ Role & HomeAuthorizationService        │  │
│  └───────────────────────┘  └────────────────────────────────────────┘  │
│  ┌───────────────────────┐  ┌────────────────────────────────────────┐  │
│  │ REST Controllers      │  │ SqlConsoleService (DML Scoping Engine) │  │
│  └───────────────────────┘  └────────────────────────────────────────┘  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ JDBC / HikariCP
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                            Data Persistence Layer                       │
│                   Oracle Database 21c Express Edition                   │
│                                                                         │
│  • 17 Relational Tables (Normalized EER Master Schema)                  │
│  • Sequences (SEQ_USER_ID, SEQ_HOME_ID, SEQ_DEVICE_ID, etc.)           │
│  • PL/SQL Stored Procedures & Functions                                 │
│  • Triggers (TRG_PREVENT_DEVICE_CYCLE)                                  │
└─────────────────────────────────────────────────────────────────────────┘
```

### Authentication Architecture Flow:
```
1. Client (Google Sign-In / Email Password) ──► Firebase Auth
2. Firebase Auth ──► Returns Firebase ID Token (JWT)
3. Client ──► Sends Bearer Token to Spring Boot (`/api/auth/me`)
4. FirebaseAuthenticationFilter ──► Verifies Token with Firebase Admin SDK
5. UserProvisioningService ──► Resolves / Provisions User in Oracle USERS Table
6. Spring Security ──► Sets SecurityContext with Verified Role (ADMIN / USER)
```

## Authentication

The platform supports dual-provider authentication:

1. **Continue with Google (OAuth 2.0):**
   - Pop-up Google identity prompt via Firebase SDK.
   - Client acquires signed Firebase ID Token and transmits it in the `Authorization: Bearer <token>` header.
   - Backend verifies token signature, claims, and expiration with the Firebase Admin SDK.
   - Automatically provisions/links user account in Oracle `USERS` table with role assignment.
2. **Email & Password Authentication:**
   - Sign up with email and password or sign in with existing credentials.
   - Includes real-time validation and self-service **Password Reset** email delivery via Firebase.
   - Issues verified ID token consumed by Spring Boot `/api/auth/me`.

## Authorization

- **`ADMIN` Role:** Global administrative visibility across all registered residences, devices, rules, alerts, and system-wide SQL DML capabilities.
- **`USER` Role:** Restricted strictly to homes explicitly granted to the user in the `HOME_ACCESS` table. All entity queries (`/api/homes`, `/api/rooms`, `/api/devices`, `/api/alerts`, `/api/rules`, `/api/sql-console`) enforce home authorization server-side.
- **Zero-Home Handling:** Users with no access grants are presented with a clean onboarding interface offering home creation or invitation joining.

## SQL Console & Scoped DML

The SQL Console (`SqlConsole.jsx`) located on the Home Details page allows interactive database execution:

```
┌────────────────────────────────────────────────────────────────────────┐
│ SQL CONSOLE                           [ADMIN · FULL] / [USER · SCOPED] │
├────────────────────────────────────────────────────────────────────────┤
│ [ SELECT ]  [ INSERT ]  [ UPDATE ]  [ DELETE ]  [ PL/SQL ]             │
│                                                                        │
│ Templates: [Devices in Home] [Active Alerts] [Thermostat Modes] ...    │
│                                                                        │
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │ SELECT device_name, status, room_id FROM devices                   │ │
│ └────────────────────────────────────────────────────────────────────┘ │
│                                                                        │
│ SQL operations are restricted to homes you can access.     [ RUN SQL ] │
└────────────────────────────────────────────────────────────────────────┘
```

### Security & Permission Policy:
- **`ADMIN`:** Real database `SELECT`, `INSERT`, `UPDATE`, `DELETE`, and approved PL/SQL routines.
- **`USER`:** Real database `SELECT`, `INSERT`, `UPDATE`, `DELETE`, and approved PL/SQL routines **strictly scoped to authorized homes**.
- **Identity Lockdown:** Direct access to `USERS`, `USER_CONTACT_NUMBERS`, and `HOME_ACCESS` is **unconditionally prohibited** for regular users.
- **Dangerous SQL Prohibitions:** `DROP`, `ALTER`, `TRUNCATE`, `CREATE`, `RENAME`, `COMMENT`, `GRANT`, `REVOKE`, `BEGIN`, `DECLARE`, `EXEC`, `DBMS_*`, `UTL_*`, `SYS.*`, and multi-statement queries are strictly rejected for all users.
- **Confirmation Safety:** Explicit confirmation modal prompt required before executing any `UPDATE`, `DELETE`, or state-modifying procedure.

## PL/SQL Procedures, Functions & Triggers

The system leverages compiled Oracle PL/SQL objects:

1. **`FN_CALCULATE_DEVICE_UPTIME(p_device_id)` (Function):**
   Computes derived uptime intervals (`X days, Y hours, Z minutes`) by comparing `SYSTIMESTAMP` against `last_restart_time` or `install_date`.
2. **`FN_CHECK_DEVICE_ACCESS(p_user_id, p_device_id)` (Function):**
   Evaluates M:N authorization across `HOME_ACCESS`, `ROOMS`, and `DEVICES`, returning `1` (authorized) or `0` (denied).
3. **`SP_ACKNOWLEDGE_ALERT(p_alert_id, p_user_id)` (Procedure):**
   Locks alert row via `FOR UPDATE NOWAIT`, verifies pending state, and updates status to `ACKNOWLEDGED` with audit timestamps.
4. **`SP_HOME_DEVICE_HEALTH_REPORT(p_home_id)` (Procedure):**
   Uses an **explicit cursor** (`CURSOR c_devices IS ...`) to iterate across all room devices and streams formatted diagnostic lines via `DBMS_OUTPUT`.
5. **`SP_RECORD_SENSOR_READING(p_device_id, p_value, p_reading_id OUT)` (Procedure):**
   Fetches surrogate `reading_id` from `SEQ_READING_ID.NEXTVAL` and inserts weak entity metric.
6. **`TRG_PREVENT_DEVICE_CYCLE` (Trigger):**
   `BEFORE INSERT OR UPDATE OF parent_device_id ON DEVICES` trigger blocking circular self-parent hierarchy assignments (`ORA-20030`).

## Troubleshooting

- **Oracle Connection Refused (`ORA-12541` / `Connection refused`):** Verify Oracle XE service is running (`Get-Service OracleServiceXE`) and listening on port `1521`.
- **Firebase Token Verification Failed (`401 Unauthorized`):** Verify `GOOGLE_APPLICATION_CREDENTIALS` points to a valid service account JSON key and the client token is not expired (Firebase tokens expire after 1 hour).
- **CORS Errors in Browser Console:** Verify `CORS_ALLOWED_ORIGINS` in `backend/src/main/resources/application.properties` includes `http://localhost:5173`.
- **Circular Identifier in application.properties:** Ensure environment variable keys do not map identically to placeholder names without prefixes (e.g. use `ADMIN_GOOGLE_EMAIL` directly via Spring `Environment`).

## Security Notes

1. **Never commit server secrets:** `.env`, `*service-account*.json`, and private keys are ignored via `.gitignore`.
2. **Never hardcode database passwords:** Always supply `DB_PASSWORD` via runtime environment variables.
3. **Frontend tokens are public:** `VITE_` variables in `frontend/.env` are bundled into client JavaScript and must only contain public identifiers.
4. **Backend-authoritative authorization:** All ownership and role checks are enforced in Spring Boot and Oracle SQL/PLSQL, never delegated to client state.
